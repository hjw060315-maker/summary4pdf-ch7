# PDF 요약 웹 앱 설계

- 상태: 검토 에이전트 확인 완료, 사용자 승인 대기
- 기준 문서: `docs/prd.md` (요구사항의 기준). 이 문서는 PRD를 **어떻게 만들지**를 정한다.
- 표기: **[사용자 결정]** = 사용자가 직접 정함, **[내 판단]** = 설계 중 내가 정한 것(사용자가 고칠 수 있음), **[빌더 몫]** = 만드는 에이전트가 정함

## 0. PRD와 이 문서의 관계

- 계획을 세우고 만드는 쪽은 **`docs/prd.md`를 함께 읽는다.** 오류 문구, 외부 전달 안내 문구, 요점 개수·키워드 규칙, 수용 기준(F1~F6)의 원문은 PRD에 있다.
- 두 문서가 어긋나면 이 설계 문서가 **이미 PRD에 반영된 결정**(4MB, 두 모델 폴백, 앞부분만 사용)을 다시 확인한 것이므로 같은 내용이다. 그 밖에서 어긋나면 **PRD가 우선**하고, 어긋남을 보고한다.
- 이 문서에서 PRD와 다르게 정한 것은 한 가지뿐이다: 7장의 `EMPTY_PDF`/`NO_TEXT` 구분(**[내 판단]**).
- PRD 10장의 Q11(무료 모델 제공사의 데이터 정책 확인)은 안내 문구에만 영향을 준다. 결과에 따라 모델을 바꾸지 않는다(무료 모델 두 개로 고정). 확인 전에는 PRD 6.4의 문구를 그대로 쓴다.

## 1. 의도와 이유

대학생이 논문·강의자료 PDF를 올리면 AI가 한 줄 요약, 핵심 요점, 키워드를 보여 주는 웹 앱이다. 사용자는 이 요약을 먼저 훑고 그 PDF를 정독할지 판단한다. 목표는 "정독할 문서인가"를 짧은 시간에 결정하게 돕는 것이다.

## 2. 목표, 비목표, 하지 말아야 할 것

목표
- 정상 PDF(텍스트 있음)를 올리면 60초 안에 요약 화면(한 줄 요약, 핵심 요점, 키워드)이 나온다.
- 요약 길이를 짧게/보통/자세히로 고를 수 있다.
- 무료 모델이 실패해도 앱이 멈추지 않고, 사용자가 이해할 수 있는 한국어 안내가 나온다.

비목표 (PRD 7장 범위 밖)
- 요약 저장·목록, 로그인, 원문 정보(페이지 수·글자 수)·파일 이름 표시, 요약 복사·다시 요약하기 버튼.
- 스캔 PDF(OCR), 여러 파일 동시 처리, 요약 언어 선택.

하지 말아야 할 것 (실패로 보는 경우)
- 올린 PDF나 요약, 추출한 텍스트를 서버에 저장하거나 로그에 남기는 것.
- 사용자에게 깨진 결과, 빈 화면, 내부 오류 원문, 키·서버 주소를 보여 주는 것.
- 문서에 없는 내용을 지어낸 요약을 "사실"처럼 보여 주는 것(그래서 부정확할 수 있다는 안내가 필요하다).

## 3. 제약

- 플랫폼: Next.js(App Router, TypeScript), GitHub 저장소 `summary4pdf-ch7`, Vercel 배포. **[사용자 결정]**
- 업로드 상한 **4MB**: Vercel 함수 요청 본문 기본 한도가 4.5MB(초과 시 413)라서 업로드를 4MB로 막는다. **[사용자 결정]** 쪽수 상한 50쪽은 PRD대로.
- 함수 실행 시간: Vercel Hobby 플랜도 최대 300초(fluid compute 기준 문서)라서 PRD의 60초 목표는 가능하다. 요약 라우트에 최대 실행 시간을 **60초**로 명시한다. **[내 판단]**
- AI: OpenRouter 무료(`:free`) 모델만 사용한다. 첫 번째 `nvidia/nemotron-3-ultra-550b-a55b:free`, 응답이 없거나 오류(429 포함)면 두 번째 `nvidia/nemotron-3.5-super-vl:free`로 한 번 넘어간다. 키는 환경 변수 `OPENROUTER_API_KEY`. **[사용자 결정]**
- `.env`는 열거나 출력하지 않는다(프로젝트 규칙). 값은 대화·로그·문서·커밋에 남기지 않고 변수 이름만 쓴다. Vercel에는 사용자가 환경 변수를 직접 등록한다.
- 처리 시간 예산 **[내 판단]**: 요청 하나에 **전체 마감 시간**을 둔다. 라우트 최대 실행 시간은 60초이고, 응답을 돌려줄 여유를 두고 **전체 마감은 약 55초**로 한다. 추출은 약 10초 이내를 목표로 하고, 모델마다 제한은 최대 25초이되 **남은 시간이 25초보다 적으면 남은 시간만큼만** 준다. 마감이 지나 실패했으면 `TIMEOUT`, 그 밖의 모든 실패(한도·장애·형식 오류)로 두 모델이 다 실패했으면 `AI_BUSY`로 답한다. 실제 응답 시간을 재 보고 숫자는 조정할 수 있다.
- 모델 이름 **[사용자 결정]**: 두 모델 이름은 사용자가 지정했다. 에이전트가 **임의로 바꾸지 않는다.** 이름이 틀렸거나 무료 제공이 끝났으면 바꾸지 말고 보고해 사용자 승인을 받는다. 첫 번째 모델은 이전 프로젝트(공감 다이어리)에서 실제 호출이 성공했지만, 두 번째 모델은 아직 실제 호출을 해 보지 않았다. 그래서 **ai-integration-specialist의 첫 작업**으로 두 모델의 실제 호출 가능 여부와 텍스트 입력만으로 JSON 응답이 안정적인지를 점검한다(예시 문장 사용).
- 업로드 4MB와 플랫폼 본문 한도 4.5MB 사이는 multipart 오버헤드를 고려한 여유이다. 4MB에 가까운 파일에서 실제로 문제가 없는지는 backend가 배포 전에 확인한다. 화면은 업로드 전에 4MB를 먼저 검사한다(9장).

## 4. 접근 방식 (검토한 것)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 한 번의 요청으로 처리 (선택)** | 화면이 PDF를 한 번 보내면 서버가 추출→요약을 차례로 처리하고 결과를 돌려줌 | PRD의 "서버에 남기지 않음"과 잘 맞음, 실패 지점이 적음, 구역 분리가 쉬움 | 진행 단계를 정확히 알리지 못함("요약하는 중이에요" 한 가지) |
| B. 두 단계로 나누기 | 먼저 추출, 텍스트를 화면이 받아 다시 요약 요청에 실어 보냄 | 단계 표시가 정확 | 텍스트가 화면을 오가고, 요청이 두 번, 조작된 텍스트 위험 |
| C. A + 스트리밍 | 한 요청 안에서 단계 소식을 흘려 보냄 | 정확한 진행 표시 | 구현·시험이 가장 복잡, PRD 완료 기준에 불필요 |

선택: **A** **[사용자 결정]**. 이유: PRD 범위(저장 없음, 단순한 완료 기준)에 가장 맞고 구역이 깔끔하게 나뉜다.

## 5. 전체 구조

```
브라우저(화면) --POST /api/summarize (multipart: file, length)--> 라우트(글루)
   1) 입력 검증(크기·형식)          [backend]
   2) PDF 텍스트 추출               [backend]  extractText()
   3) AI 요약                       [ai]       summarize()
   <-- JSON: 요약 결과 또는 오류 --
```

- 서버는 아무것도 저장하지 않는다. 파일과 텍스트는 메모리에서만 처리하고 요청이 끝나면 버려진다.
- 요청을 받는 라우트 한 곳(`src/app/api/summarize/route.ts`)이 두 함수를 이어 붙인다. 라우트는 backend 소유.

## 6. 구역과 에이전트 (서로 다른 파일만 고친다)

| 구역 | 에이전트 | 파일 | 하는 일 |
|---|---|---|---|
| 서버·추출 | backend-developer | `src/app/api/**`, `src/server/**`, `tests/server/**` | 업로드 받기, 4MB·PDF 형식·50쪽 검증, 텍스트 추출, 스캔/빈/암호/손상 PDF 판별, 라우트 연결, 오류 응답 형태 |
| AI | ai-integration-specialist | `src/ai/**`, `tests/ai/**` | OpenRouter 호출, 모델 폴백, 프롬프트, JSON 파싱·검증, 입력 길이 자르기, 프롬프트 주입 방어 |
| 화면 | frontend-developer | `src/app/**`(api 제외), `src/ui/**`, `tests/ui/**` | 끌어 놓기 업로드 화면, 길이 선택, 외부 전달 안내, 진행 표시, 요약 결과, 오류 안내(모두 한국어) |
| 공통 약속 | backend-developer가 관리 | `src/shared/**`, `docs/API.md` | 타입, 상수(4MB, 50쪽, 요점 개수 등), 오류 코드. 바꾸려면 세 담당이 합의 |
| 검증 | qa-engineer | `docs/qa-report.md` (코드는 고치지 않음) | 시험·보고. 문제는 담당 개발 에이전트가 고친다 |

- `package.json`, 설정 파일은 backend-developer만 고친다(새 패키지는 그가 설치).
- 착수 순서 **[내 판단]**: ① backend-developer가 프로젝트 뼈대, `src/shared/**`(타입·상수·오류 코드), `docs/API.md`를 먼저 만들어 고정한다 → ② 그 약속을 기준으로 backend(추출·라우트)·ai·frontend가 **동시에** 각자 구역만 고친다(ai는 모의 응답, frontend는 모의 데이터로 단독 시험) → ③ 세 구역을 연결 → ④ qa-engineer 시험과 수정·재확인 반복 → ⑤ 배포. 공통 약속(`src/shared`, API.md)을 바꿀 때는 세 담당이 합의한다.
- **빌더 몫**: 텍스트 추출 라이브러리 선택. 조건은 Vercel Node 서버에서 도는 것, 네이티브 의존성이 없는 것, 암호·손상 PDF를 오류로 구분할 수 있는 것이다. 후보는 `unpdf`, `pdfjs-dist`.

## 7. 요청·응답 약속 (초안, 확정은 `docs/API.md`)

`POST /api/summarize` — `multipart/form-data`
- `file`: PDF 1개 (필수)
- `length`: `short` | `normal` | `long` (필수, 기본 `normal`)

성공 응답 `200`
```json
{
  "oneLine": "문서 전체를 한 문장으로",
  "points": ["핵심 요점 …"],
  "keywords": ["키워드", "…"],
  "truncated": false
}
```
- `points`: 짧게 3개, 보통 4개, 자세히 5개(문장 길이도 차이). `keywords`: 5~10개.
- `truncated`: 텍스트가 길어 **앞부분만 사용**했으면 `true`(화면에 "문서가 길어 앞부분을 기준으로 요약했어요" 표시).

오류 응답 `{ "error": { "code": "...", "message": "한국어 안내" } }`

| code | HTTP | 상황 | 안내 (PRD) |
|---|---|---|---|
| `NOT_PDF` | 400 | PDF가 아님 | PDF 파일만 올릴 수 있어요 |
| `FILE_TOO_LARGE` | 413 | 4MB 초과 | 파일이 너무 큽니다(최대 4MB, 50쪽) |
| `TOO_MANY_PAGES` | 400 | 50쪽 초과 | 파일이 너무 큽니다(최대 4MB, 50쪽) |
| `UNREADABLE_PDF` | 422 | 암호·손상 | 파일을 열 수 없습니다 |
| `NO_TEXT` | 422 | 쪽은 있는데 텍스트 없음(스캔 등) | 텍스트를 읽을 수 없는 PDF입니다. 텍스트가 포함된 PDF를 올려 주세요 |
| `EMPTY_PDF` | 422 | 0쪽·내용 없음 | 내용이 없는 PDF입니다 |
| `AI_BUSY` | 503 | 두 모델 모두 실패(한도·장애·형식 오류) | 지금 요약 서비스가 혼잡합니다. 잠시 후 다시 시도해 주세요 |
| `TIMEOUT` | 504 | 시간 초과 | 요약이 오래 걸려 중단했습니다. 잠시 후 다시 시도해 주세요 |
| `BAD_REQUEST` | 400 | `length` 값 오류, 파일 없음 | 요청이 올바르지 않아요 |

- **쪽수 상한 처리 [내 판단]**: 50쪽을 넘으면 **거절**(`TOO_MANY_PAGES`)한다. 50쪽까지만 쓰는 방식은 쓰지 않는다. `truncated`는 쪽수가 아니라 **추출한 텍스트가 모델 입력 길이를 넘을 때만** 쓴다. 쪽수를 먼저 가볍게 센 뒤(전체 텍스트 추출 전에) 상한을 넘으면 바로 거절한다. 쪽수를 세는 구체적인 방법은 [빌더 몫].
- 스캔 PDF와 완전히 빈 쪽이 있는 PDF는 텍스트가 없다는 점에서 구분하기 어렵다. 그래서 `EMPTY_PDF`는 쪽 수가 0이거나 구조상 내용이 없을 때만, 쪽은 있으나 텍스트가 없으면 `NO_TEXT`로 처리한다. **[내 판단]** (PRD는 "스캔"과 "빈 PDF"를 따로 안내했지만, 둘을 믿을 만하게 가를 방법이 없어 이렇게 정함)
- 플랫폼 413(본문 4.5MB 초과) 응답은 JSON이 아닐 수 있으므로 화면이 업로드 전에 4MB를 먼저 검사하고, 그래도 413이 오면 `FILE_TOO_LARGE`와 같이 안내한다.

## 8. AI 요약 동작

- `summarize({ text, length }) → { oneLine, points, keywords, truncated }`, 둘 다 실패하면 `AiUnavailableError`.
- 순서: 첫 번째 모델 → 실패(응답 없음, HTTP 오류·429, 시간 초과 25초, 빈 응답, JSON 형식 오류, 값 범위 위반)하면 두 번째 모델 → 실패하면 오류. 같은 모델을 반복해서 부르지 않는다(PRD의 "재시도 1회" = 모델 전환).
- 입력이 길면 앞부분만 사용하고 `truncated: true`. 문자 수 상한은 모델의 처리 가능 길이에 맞춰 **[빌더 몫]**(시작값 제안: 약 30,000자).
- 프롬프트: 요약은 한국어로, 문서에 없는 내용을 지어내지 않기, JSON으로만 답하기. 문서 텍스트는 명령이 아니라 **자료**로만 다루고, 문서 안의 지시문은 따르지 않는다(프롬프트 주입 방어).
- 로그에는 모델 이름과 오류 종류만 남기고 문서 내용과 키는 남기지 않는다.
- 요약 언어는 한국어로 고정(영어 논문도 한국어 요약). PRD 9장·Q4.

## 9. 화면

- 한 페이지(`/`)로 구성: 제목·설명 → 외부 전달 안내(올리기 전에 항상 보임) → 끌어 놓기 영역(클릭해서 선택도 가능) → 길이 선택(짧게/보통/자세히, 기본 보통) → [요약하기] → 진행 표시("요약하는 중이에요, 최대 1분쯤 걸릴 수 있어요") → 결과 또는 오류.
- 결과: 한 줄 요약, 핵심 요점(목록), 키워드, "AI 요약은 부정확할 수 있으니 중요한 내용은 원문을 확인하세요", `truncated`면 앞부분 기준 안내. 원문 정보와 파일 이름, 복사·다시 요약 버튼은 없다(PRD).
- 올리기 전에 클라이언트에서 PDF 형식과 4MB를 먼저 검사한다(서버 검증은 별도로 유지).
- 반응형(375px~데스크톱), 키보드로 파일 선택·길이 선택·요약 시작 가능, 진행·오류는 색에만 의존하지 않고 글로도 전달, 오류 문구는 원인과 다음 행동을 알려 준다(PRD F6).
- 디자인 톤(색·글꼴)은 **[빌더 몫]**: 깔끔하고 읽기 편하게.

## 10. 시험 (qa-engineer)

시험 항목: 정상 PDF(텍스트 있음, 짧은 것·긴 것), 길이 3종, 4MB 초과, 50쪽 초과, PDF가 아닌 파일(확장자만 .pdf인 것 포함), 스캔 PDF, 빈 PDF, 암호 PDF, 손상 PDF, 앞부분만 쓰는 긴 텍스트, 첫 번째 모델 실패 → 두 번째 모델, 두 모델 모두 실패, 형식이 깨진 AI 응답, 시간 초과, 문서 안의 프롬프트 주입 문장, 파일·텍스트가 로그와 저장소에 남지 않는지, 모바일 폭과 키보드 조작.
- 모델과 네트워크를 모의로 바꾼 자동 시험과, 실제 OpenRouter를 부르는 점검 스크립트(예시 문서 3개, 개인정보 없음)를 둔다.
- QA는 보고만 하고, 개발 에이전트가 고친 뒤 QA가 다시 확인한다. **높음 항목이 모두 고쳐지고 다시 통과할 때까지 반복**한다. 보고서는 `docs/qa-report.md`에 심각도별로 쓴다.

## 11. 배포

- 코드는 `summary4pdf-ch7`(공개)에 올리고, Vercel을 이 저장소에 연결해 배포한다.
- 요약 라우트는 최대 실행 시간 60초를 명시한다.
- Vercel 프로젝트 설정에서 `OPENROUTER_API_KEY`를 환경 변수로 등록한다. **사용자가 직접** 한다(키 값은 화면·대화에 옮기지 않는다).
- Vercel 계정 연결과 프로젝트 생성은 사용자의 계정 작업이다. 에이전트는 코드와 설정, 배포 후 점검을 맡는다.
- 배포 주소에서 정상 PDF가 요약되는지 처음부터 끝까지 확인한다.

## 12. 구현 전·중에 확인할 일

- PRD Q11: 무료 모델 제공사가 입력 데이터를 학습·보관하는지 확인하고, 안내 문구에 반영한다(사용자 또는 PM).
- 실제 응답 시간이 60초 목표에 맞는지 실제 PDF로 측정하고, 필요하면 모델별 제한 시간과 입력 길이 상한을 조정한다.

## 13. 빌더에게 맡기는 것

- 텍스트 추출 라이브러리, 문자 수 상한의 정확한 값, 프롬프트 문구, 화면 디자인(색·간격·글꼴), 컴포넌트 나누기, 시험 도구(vitest 등), 폴더 세부 구조.
