## 3. 발견 사항

높음, 중간은 없다.

### 낮음 1. 업로드 화면에 선택한 파일 이름이 표시됨
- 위치: `src/ui/components/UploadForm.tsx:89`
- 내용: 검토 3은 "파일 이름은 화면과 로그 어디에도 나오지 않는다"고 적었다. 화면에서 `선택한 파일: {file.name}`이 나온다. PRD와 설계(PRD 96행, 설계 130행)는 파일 이름을 "요약 결과 화면"에서만 제외한다. 이름은 브라우저 안에만 있고 서버·로그로 가지 않는다(#19).
- 재현: 파일을 고르면 이름이 보인다.
- 제안: 의도된 동작이면 계획 문구를 "결과 화면과 로그"로 고친다. 이름까지 숨겨야 하면 이 줄을 "PDF 1개 선택됨"으로 바꾼다. 사용자 확인이 필요하다.

### 낮음 2. 첫 모델 시간 초과가 잦아 응답이 느림
- 위치: `src/ai/summarize.ts:199-229`, `src/shared/constants.ts:178` (`MODEL_TIMEOUT_MS` 25초)
- 내용: 시험 중 첫 모델이 25초 시간 초과를 낸 경우가 11회 중 2회 있었다. 이때 총 응답이 28~35초였다. 정상 동작이고 55초 마감 안이지만 두 번째 모델도 느리면 마감에 가까워진다. 무료 모델 상태에 따라 달라지는 문제다.
- 재현: 50쪽 PDF를 short로 올리면 35초 걸렸다. 단, 모델 상태에 따라 달라진다.
- 제안: 필수 수정은 아니다. 느린 첫 모델이 계속되면 첫 모델 시간 제한을 줄이거나 화면 진행 문구에 "최대 1분"을 알려 주는 것을 검토한다.

### 낮음 3. 본문 크기 검사가 본문을 다 읽은 뒤에 이루어짐
- 위치: `src/app/api/summarize/route.ts:18`, `src/server/summarize-service.ts` (`file.size` 검사)
- 내용: `request.formData()`가 본문을 먼저 모두 읽고 나서 크기를 본다. 플랫폼의 4.5MB 본문 제한이 있어 영향은 작다. 413 응답은 잘 나왔다(#6).
- 제안: 배포 환경에서 본문 제한이 실제로 작동하는지 Task 9에서 확인한다.

## 4. 못 한 것과 이유

- 브라우저 화면 조작(모바일 폭 실측, 키보드 Tab/Enter/Space, 파일 끌어놓기): 브라우저가 없다. 컨트롤러가 시각 점검을 했고 UI 단위 시험(`tests/ui`)은 통과했다.
- 실서버의 55초 마감과 TIMEOUT 504: 응답 지연을 일부러 만들 안전한 방법이 없다. 단위 시험으로만 확인했다.
- 깨진 AI 응답의 실서버 시험: 같은 이유로 단위 시험만 했다.
- Vercel 배포 환경의 413 비JSON 응답, 4.5MB 본문 제한: 배포 전이라 못 했다.
- 여러 사용자가 동시에 요청하는 부하 시험: 무료 모델 한도 때문에 하지 않았다.
